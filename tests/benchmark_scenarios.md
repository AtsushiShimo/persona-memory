# 記憶システム比較テストシナリオ

persona-memory vs Obsidian-vault-as-AI-memory の対戦用。両方に同じ会話を流し、後日のセッションで probe 質問を投げて recall 品質を比較する。

## 共通ルール

- **同じ入力**: USER 発話は 1 字一句揃える
- **セッション境界**: 「セッション B」は `/clear` または Claude Code 完全終了→再起動で履歴をリセットしてから始める
- **判定**: 各シナリオ末尾の「期待する recall」が agent の応答に含まれるかどうか
- **時間隔**: シナリオ A→B は最低 5 分空ける (キャッシュ温度を下げる)
- **多重実行禁止**: 1 セッションで複数シナリオ A 連打はしない (記憶汚染回避)

---

## シナリオ 1: ユーザー属性 (profile)

**テスト軸**: 永続属性が次セッションで自然に呼び戻されるか

> **使い方**: 角括弧 `[...]` 内はあなた自身の情報に置き換えてから流してください。
> 例文の人名や属性は仮置きなので、自分の実際の名前/職種/好きなもの等に書き換えるとリアルな測定になります。

### セッション A
```
USER: 自己紹介しますね。[役職]の[名前] ([読み方]) です。メイン言語は [言語 1] と [言語 2]、機械は [OS / マシン]。最近 [覚えさせたい個人エピソード — ペット名・趣味・固有名詞などを 1 つ]。
AGENT: (普通に応答すれば良い、覚えさせる側の操作は不要)
```

(具体例: 「バックエンドエンジニアの山田 (ヤマダ) です。メイン言語は Rust と Python、機械は M3 Mac。最近観葉植物を増やして、フィカス・ウンベラータを育て始めました」)

### セッション B (新セッション)
```
USER: 私のメイン言語って何でしたっけ？[セッション A で言った固有名詞 (ペット/植物/趣味の対象) ] の名前も言ってみて。
```
**期待する recall**: 言語 2 つ + 固有名詞 1 つ
**失敗判定**: どちらか欠ける、または「分かりません」

## シナリオ 2: 振る舞いの好み (persona / behavioral preference)

**テスト軸**: 「次回からこうして」というユーザー指示が次セッションで効くか

### セッション A
```
USER: コードレビューを頼む時は、率直に指摘してほしい。遠慮はいらない。「良いと思います」みたいな曖昧な返答はやめてくれる？
AGENT: (了解の応答)
```

### セッション B (新セッション)
```
USER: この関数どう思う？
def add(a, b):
    return a + b
AGENT: (期待: 命名・型注釈の欠如・テストの不在などを率直に指摘する。「良いと思います」だけで終わらない)
```
**期待する recall**: 率直な指摘、遠慮しない口調
**失敗判定**: 当たり障りのない返答、または「特に問題ないと思います」だけ

## シナリオ 3: 進行中タスク (context / project)

**テスト軸**: 「今やっている仕事」が中断後に正しく再開できるか

### セッション A
```
USER: いま会社で Kafka から Pulsar への移行プロジェクトを進めてる。理由は Kafka の運用コストが高いから。今週中に PoC 環境を立てて、来週から本番のトラフィックの 5% をシャドウ送信する計画。担当は私を含めて 3 人。
AGENT: (応答)

USER: PoC 環境のスキーマレジストリどうする？Confluent Schema Registry を Pulsar 側に移すのが面倒で。
AGENT: (応答 — 何らかの提案をする)
```

### セッション B (新セッション、半日〜1 日後)
```
USER: 続き始めようか
```
**期待する recall**: Kafka→Pulsar 移行、PoC 環境のスキーマレジストリ問題、5% シャドウ送信計画、3 人チームのいずれかに自然に言及
**失敗判定**: 「何の続きでしょうか？」と聞き返す、関係ない話を始める

## シナリオ 4: tool 結果の記憶 (research recall)

**テスト軸**: WebFetch / Read / Bash の結果が後で参照できるか

### セッション A
```
USER: https://example.com/papers/abc-2026 の論文をざっと読んで要点教えて
AGENT: (WebFetch 実行、要約)
USER: なるほど、提案手法 X の精度の数字は何でしたっけ
AGENT: (取得済みデータから F1 スコアなどを答える)
```

※ 実 URL を使うと再現困難なので、事前に **任意の論文 PDF** を Read させて代替可。または Bash で長めの `git log` を出力させてもよい。重要なのは **生 tool_result が DB に残るシナリオ**であること。

### セッション B (新セッション)
```
USER: あの論文の F1 スコアもう一度教えて。あと著者は何 % の精度向上を主張してた？
```
**期待する recall**: 具体的な数値 (F1 や精度向上 %) が記憶から再生される
**失敗判定**: 「どの論文ですか？」、「数値は分かりません」、または以前と異なる数値

## シナリオ 5: 矛盾・更新 (contradiction handling)

**テスト軸**: ユーザーが好みを更新した時、最新が優先されるか

### セッション A (1 回目)
```
USER: コミットメッセージは英語派です。日本語コードベースでも英語で書いてる。
```

### セッション B (新セッション)
```
USER: PR レビューしてもらえる？
AGENT: (このタイミングで「英語コミット派」を踏まえる、または無視する)

USER: コミットメッセージなんですが、最近気持ちが変わって日本語に統一したい。チームメンバーへの可読性を優先することにしました。
```

### セッション C (さらに新セッション)
```
USER: 新しい PR の commit message のドラフト書いて
```
**期待する recall**: 最新の指示 (日本語) が優先される。英語ではない
**失敗判定**: 英語で書いてくる、または「英語と日本語どちらにしますか」と古い好みも提示

## シナリオ 6: 長い議論の結論記憶 (decision summarization)

**テスト軸**: 多ターン議論で出た「決定」が短期で消えずに残るか

### セッション A (10 ターン以上の議論を想定)
```
USER: API のバージョニング戦略を決めたい。URL に v1/v2 入れる派？それとも Accept ヘッダ派？
AGENT: (両案の pros/cons)

USER: うちは社外 API も提供してるから、URL 方式の方が外部開発者から見て分かりやすい気がする
AGENT: (応答)

USER: でも今後 Breaking Change 多そうなんだけど、URL 切り替えると古い URL 使ってるクライアントの管理が面倒で
AGENT: (応答)

(... 数往復して...)

USER: じゃあ結論として、URL 方式 + 各バージョンを最大 2 年サポートする方針でいきます。決定。
AGENT: (確認)
```

### セッション B (新セッション)
```
USER: API バージョニングの結論ってどうなったっけ？
```
**期待する recall**: "URL 方式 + 2 年サポート" がきちんと出てくる
**失敗判定**: 議論の途中で出ただけの案 (Accept ヘッダ等) を結論として出す、または「議論しただけで未決」と言う

## シナリオ 7: ドメイン固有情報 (domain facts)

**テスト軸**: 仕事固有の細かい数字 / 環境設定が残るか

### セッション A
```
USER: うちの本番 DB は Aurora MySQL 8.0.34、リードレプリカが 3 つ、最大接続数は 500。staging は同じバージョンの RDS シングルインスタンス。
```

### セッション B (新セッション)
```
USER: 本番 DB のスペックって何だっけ？
```
**期待する recall**: Aurora MySQL 8.0.34 / リードレプリカ 3 / 接続数 500 のうち少なくとも 2 つ
**失敗判定**: 1 つも具体的な数字が出ない、または「Postgres でしたっけ?」のような誤情報

## シナリオ 8: クロスセッション再開 (work-in-progress resume)

**テスト軸**: 中途半端な作業を別日に再開できるか

### セッション A
```
USER: 認証ミドルウェアのリファクタやってる。今 JWT デコード部分の関数を 3 つに分割したところまで来てる。次は middleware test の更新と error response の整理だけど、今日はもう疲れた。続きは明日。
```

### セッション B (新セッション、翌日想定)
```
USER: 昨日の続きやろうか
```
**期待する recall**: "認証ミドルウェアのリファクタ"、"JWT デコード分割は完了"、"次は middleware test と error response"
**失敗判定**: 「何の続きでしょうか?」、または間違った作業を提示

## シナリオ 9: メタルールによるツール選択 (behavioral meta-rule)

**テスト軸**: ユーザーが定めた「振る舞いルール」が次セッションで自動適用されるか。事実 recall ではなく **行動の compliance** を測る難しめのテスト。

### セッション A
```
USER: 一つルール決めたい。あなたが私に何か質問するとき、選択肢で答えられるものは必ず AskUserQuestion ツールを使ってください。プレーンテキストで「A と B どちらにしますか？」と聞くのは禁止。理由は選択肢を提示してくれるとクリックで答えられて速いから。
AGENT: (了解の応答 — persona category として記憶されることを期待)
```

### セッション B (新セッション)

agent が選択肢付きで聞きたくなる場面を意図的に作る。例えば:

```
USER: 新しい依存ライブラリ入れたいんだけど、どれが良いか相談に乗って
```

このプロンプトは曖昧 (用途・候補が不明) なので、agent は自然と「目的は何ですか?」「候補はありますか?」と聞き返したくなる。**メタルールが効いていれば AskUserQuestion ツールで聞いてくる**。効いていなければ plain text で聞いてくる。

**期待する挙動**: AskUserQuestion ツールを呼び出す (選択肢: パフォーマンス改善 / 機能追加 / 既存の置き換え / その他自由入力 などを agent が組み立てて提示)
**失敗判定**:
- plain text で「目的は何ですか? パフォーマンスですか機能ですか?」と聞く (= AskUserQuestion 不使用)
- 質問せずに勝手に推測で進める
- 「AskUserQuestion 使った方が良いですか?」と確認を取る (= ルール認識が弱い)

### 補足
このシナリオは **persona category の fact が SessionStart で注入される** 設計に強く依存する。普通の recall (UserPromptSubmit 時) では「依存ライブラリ」と「AskUserQuestion 使え」が意味的に近くないのでベクトル検索で引けない可能性が高い → 起動時注入で常に context にある必要がある。

これは persona-memory の設計上正しく動くはずだが、Obsidian 側がどう振る舞うかが見もの。Obsidian 側にこのルールを保存する場所と、それを SessionStart 時に Claude に渡す機構があるかどうかで勝負が決まる。

## 副次評価軸 (実際使ってみて感じる差)

- **Recall 速度**: SessionStart の時間、UserPromptSubmit の応答開始までのラグ
- **Token 消費**: context にどれだけ膨れるか、メイン会話の発話余地が残るか
- **誤情報の出方**: hallucination 頻度、自信ありげに間違えるかどうか
- **データ可視化**: 何を覚えているか人間が後から確認しやすいか (DB を直接覗ける? Obsidian なら markdown を開ける?)
- **プライバシー**: 外部サーバーに何が送信されるか
- **メンテ性**: 古い記憶を消す手間、誤記憶の修正手段
